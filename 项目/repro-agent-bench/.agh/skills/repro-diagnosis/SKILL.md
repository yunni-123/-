# 可复现性诊断方法论（repro-diagnosis）

诊断对象：科研计算仓库（`main.py` + `requirements.txt`，可选论文宣称的期望数值）。
诊断工具：`repro-tools` MCP 服务器（`inspect_repo` / `build_env` / `run_repo` / `compare_numbers` / `diagnose`）。

## 诊断流程（必须按顺序，6 步闭环）

1. **① 规划：先读仓库，定复现方案。** 调用 `inspect_repo` 获取文件结构、入口、依赖清单、
   目标数值与期望关键值（`expected_key_values`，来自同仓 pristine 基线）。
   明确「我要验证哪些数值」。
2. **② 环境构建：先校验依赖，再看代码。** 调用 `build_env`。
   若存在无法解析的版本（typo 包、不存在的版本）→ 直接判定「依赖版本问题」，
   **不要继续跑主程序**（此类缺陷主程序照常运行、无任何输出异常，只有环境校验能发现）。
3. **③ 执行：主程序必须跑两次。** 调用 `run_repo`（runs=2），采集每次的退出码/stdout/stderr/耗时。
   两次输出不一致 → 判定「随机性未固定」；只看单次输出无法发现随机性缺陷。
4. **④ 数值比对：区分「抛异常」与「静默错误」。** 调用 `compare_numbers` 把每次运行的
   关键数值与期望值比对（默认相对容差 1e-3）。
   - 抛异常 → 读异常类型与栈，定位到具体模块；
   - 不抛异常但数值偏离 → 静默错误，进入第 5 步。
5. **⑤ 根因诊断：调用 `diagnose` 汇总证据，取规则表裁决。**
   数值偏离时的优先排查顺序：**单位换算 → 数组形状/截断 → 数值稳定性（条件数、显式求逆）**。
   指标异常高（如 R² 接近 1 得反常）时优先怀疑**数据泄漏**（目标派生特征、划分前标准化）。
   若置信度 < 0.7 → **不得下结论**：回退换假设重跑（更换容差、读取更多代码、复跑），
   仍不足则输出「未知」并声明证据缺口。
6. **⑥ 修复验证：应用建议 → 重跑 → 确认是否复现。** 按 `diagnose` 的修复建议生成修复
   （固定随机种子 / 修正单位系数 / 恢复完整数组 / 锁定依赖版本等），在**不修改原仓库**的
   前提下验证（复制到 /tmp 或新建补丁文件运行），确认数值回到期望且两次运行一致。
   原仓库保持只读。

## 根因标签表（必须逐字使用，与基准集对齐）

| 标签 | 典型签名 |
|---|---|
| 可复现（无缺陷） | 依赖可解析、两次运行一致、数值在容差内 |
| 随机性未固定 | 两次运行关键数值/输出不一致 |
| 数据泄漏（目标泄漏特征） | 指标异常高（如 R² 反常接近 1）、特征由目标派生 |
| 单位换算错误 | 数值稳定偏离，偏差倍数呈常数（100/1000 等） |
| 数值不稳定 | 残差/误差量级异常、条件数高、显式求逆 |
| 静默截断 | 主程序正常退出，数值或形状与期望不符，无报错 |
| 环境不匹配 | 依赖可解析但运行时报 GPU/CUDA/backend 相关错误 |
| 依赖版本问题 | requirements 中某包/版本在环境中不可解析 |
| 未知 | 证据不足，置信度 < 0.7 |

## 硬性规则

1. 置信度 < 0.7 时不得下结论，必须回退换假设重跑或输出「未知」。
2. 报告必须包含：结论（根因标签 + 可复现性判断）、支撑证据（具体报错行/数值对比）、
   置信度、不确定性声明、「本次结论不适用的范围」。
3. 不得编造未在观测中出现的证据；证据全部来自工具返回值。
4. 诊断过程不修改被诊断仓库；修复验证只发生在 /tmp 或新建文件。
5. 「可复现性」= 同一环境下重跑结果与论文/基线一致；「缺陷」= 结果与期望不符，二者分开报告。
