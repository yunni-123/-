# 第 3 步 · 写 5 个 MCP 工具（10.05–10.06）

计算全部外置到 MCP 工具里（**因为 AGH 内核跑不了 Python**）。

## 3.1 工具清单

| # | 工具 | 输入 | 输出 | 关键点 |
|---|---|---|---|---|
| 1 | `inspect_repo` | repo_path | 结构、入口、依赖、目标数值 | 解析 `requirements.txt` |
| 2 | `build_env` | repo_path | 依赖是否可解析 / 失败原因 | **★ 检出 `dep_typo` 的唯一途径** |
| 3 | `run_repo` | repo_path | 退出码、stdout、stderr、耗时 | **跑两次**用于判随机性 |
| 4 | `compare_numbers` | actual, expected | 相对误差、是否超阈值 | 数值比对 |
| 5 | `diagnose` | 前四步的证据 | 根因标签 + 置信度 + 修复建议 | **★ 核心推理步骤** |

## 3.2 根因标签必须固定（与基准集对齐）

```python
ROOT_CAUSES = [
    "可复现",                       # 无缺陷
    "随机性未固定",
    "数据泄漏（目标泄漏特征）",
    "单位换算错误",
    "数值不稳定",
    "静默截断",
    "环境不匹配",
    "依赖版本问题",
    "未知",
]
```

> ⚠️ **标签必须和 `defect.json` 里的 `root_cause` 完全一致**，否则算不对准确率。

## 3.3 `build_env` 为什么是关键

实测发现：`dep_typo` 变体**直接跑 main.py 完全正常**，签名和完好仓库一模一样。

**只有真的去解析并校验 `requirements.txt`，才能发现 `nonexistent-package-xyz==99.99.99`。**

> 📌 **这一点写进你的技术报告**：它证明了"环境构建"是 harness 不可替代的能力，而不是多余的包装。这是你回答"换成 Python 脚本行不行"的第一张牌。

## 3.4 MCP 接入方式（重要约束）

官方文档指出：**MCP 会话路径会跳过 OAuth 绑定**。
所以**只用无需认证的本地 stdio MCP**：

```bash
node packages/cli/dist/local/agnes.mjs mcp add repro-tools \
  --stdio /usr/bin/python3 --arg /path/to/mcp_server.py
# 创建后默认停用，按 revision 依次 trust / enable
node packages/cli/dist/local/agnes.mjs mcp get repro-tools
node packages/cli/dist/local/agnes.mjs mcp trust repro-tools --expected-revision REV
node packages/cli/dist/local/agnes.mjs mcp enable repro-tools --expected-revision REV
node packages/cli/dist/local/agnes.mjs mcp tools repro-tools
```

**检查点 ③**：在 AGH 会话里能让 Agent 调用到你的 `inspect_repo`。

# 第 4 步 · 串起 6 步闭环（10.07）

在 AGH 里跑通端到端一次：

```
① 规划：读仓库，定复现方案
② 环境构建：调用 build_env        → 若依赖失败，直接判"依赖版本问题"
③ 执行：调用 run_repo（跑两次）    → 采集退出码/stderr
④ 数值比对：调用 compare_numbers   → 偏差多大
⑤ 根因诊断：调用 diagnose          → 根因标签 + 置信度
   ↳ 若置信度 < 0.7 → 回退：换假设重跑（这一步是"反馈处理"）
⑥ 修复验证：应用建议 → 重跑 → 确认是否复现
```

**验收**：对 `sinusoid-fit--pristine` 和 `sinusoid-fit--silent_truncation` 各跑一次，能得到不同结论。

# 第 5 步 · 写 `SKILL.md`（10.08）

把你（或领域专家）的排查方法论固化进去。这是"学科融合"最便宜的加分手段。

```markdown
---
name: repro-diagnosis
description: 科研计算代码可复现性诊断的标准流程与判据
---

# 诊断流程（必须按顺序）

1. **先看依赖，再看代码**。解析 requirements.txt / environment.yml 并尝试校验。
   若存在无法解析的版本，直接判定「依赖版本问题」，不要继续跑主程序。
2. **主程序必须跑两次**。两次输出不一致 → 判定「随机性未固定」。
   只看单次输出无法发现随机性缺陷。
3. **区分"抛异常"与"静默错误"**：
   - 抛异常 → 读异常类型与栈，定位到具体模块
   - 不抛异常但数值偏离 → 属于静默错误，按第 4、5 条排查
4. **数值偏离时的优先排查顺序**：
   单位换算 → 数组形状/截断 → 数值稳定性（条件数、显式求逆）
5. **指标异常高时优先怀疑数据泄漏**：
   检查是否存在由目标派生的特征；检查特征选择/标准化是否在划分之前做。
6. **置信度 < 0.7 时不得下结论**，必须回退换假设重跑，或输出「未知」。
7. **报告中必须包含**：结论、支撑证据（具体报错行/数值对比）、置信度、
   不确定性声明、以及"本次结论不适用的范围"。
8. **不得编造未在观测中出现的证据。**
```

启用：Web → 设置 → Skills → 刷新工作区 → 审核 → 启用。
然后在会话中**明确点名**："使用 repro-diagnosis 处理这个仓库"。

**检查点 ⑤**：Agent 按 Skill 的流程执行（从会话记录能看出它先查依赖、跑两次）。
